Node.js Modules: CommonJS, ES Modules & Module System

1. What is a module?
    A module is simply a reusable piece of code that can be imported into another file.
    Instead of putting everything into:
        app.js
    we split the application:
        src/
        ├── app.js
        ├── controllers/
        │   └── userController.js
        ├── services/
        │   └── userService.js
        ├── utils/
        │   └── helper.js
        └── config/
            └── db.js
    Each file can act as a module.


2. Why do we need modules?
    Imagine you have:
        // app.js
        function createUser() {}
        function deleteUser() {}
        function updateUser() {}
        function validateUser() {}
        function connectDatabase() {}
        function sendEmail() {}
    This becomes difficult to maintain.
    Instead:
        userController.js
            ↓
        userService.js
            ↓
        userRepository.js
            ↓
        database.js
    This gives you:
        separation of concerns
        maintainability
        reusability
        testability
        easier debugging
    This is exactly how your backend projects should be structured.


3. Node.js has two module systems
    CommonJS
        require()
        module.exports
        exports
    ES Modules
        import
        export
        export default


4. CommonJS
    CommonJS is the traditional Node.js module system.
    math.js
        function add(a, b) {
            return a + b;
        }
        function subtract(a, b) {
            return a - b;
        }
        module.exports = {
            add,
            subtract
        };
    app.js
        const math = require("./math");
        console.log(math.add(10, 20));
        console.log(math.subtract(20, 10));
    Output:
        30
        10


5. Exporting a single function
        function add(a, b) {
            return a + b;
        }
        module.exports = add;
    Then:
        const add = require("./math");
        console.log(add(10, 20));
    Important distinction:
        module.exports = add;
    means the module exports the function itself.
    Whereas:
        module.exports = {
            add
        };
    exports an object containing the function.


6. exports vs module.exports
    We see:
        exports.add = add;
    This works because initially:
        exports -> module.exports
    So:
        exports.add = add;
    is efficiently adding a property to:
        module.exports
    But this is dangerous:
        exports = add;
    It does not change what the module exports.
    The safer rule:
        use module.exports when we want to clearly control what the module exports.


7. ES Modules
    Modern Node.js also supports the standard Javascript module system.
    math.js:
        export function add(a,b){
            return a + b;
        }
        export function subtract(a,b){
            return a - b;
        }
    then:
        import {add, subtract} from "./math.js";
        console.log(add(2,4))   // 6


8. Default export
    We can also:
        export default function add(a,b){
            return a + b;
        }
    then:
        import add from "math.js";
    
    Notice the syntax difference:
        Named export:
            export function add() {}
            import { add } from "./math.js";
        Default export:
            export default function add() {}
            import add from "./math.js";


9. How does Node know you're using ES Modules?
    There are several ways.
    One common approach is in package.json:
        {
            "type": "module"
        }
    Then Node treats .js files as ES modules.
        Example:
            project/
            ├── package.json
            ├── app.js
            └── math.js
        package.json:
            {
                "type": "module"
            }
    Now:
        import { add } from "./math.js";
    works.


10. CommonJS vs ES Modules
    | CommonJS                                  | ES Modules                            |
    | ----------------------------------------- | ------------------------------------- |
    | `require()`                               | `import`                              |
    | `module.exports`                          | `export`                              |
    | Traditional Node system                   | JavaScript standard module system     |
    | Often `.cjs`                              | Often `.mjs`                          |
    | Can use `.js` depending on package config | Can use `.js` with `"type": "module"` |
    | `require()` is synchronous                | ESM uses static module structure      |

    Don't say:
        CommonJS is old and ESM is always better.
        Real projects still use both.


11. .cjs and .mjs
    Node gives explicit extensions:
    .cjs
    Means:
        CommonJS
        Example:
            app.cjs
    Then:
        const fs = require("fs");
    
    .mjs
    Means:
        ES Module
        Example:
            app.mjs
    Then:
        import fs from "fs";
    These extensions can remove ambiguity.


12. Node's built-in modules
    Node itself provides modules.
    For example:
        const fs = require("fs");
    or:
        import fs from "node:fs";

    Modern Node code often uses the explicit node: prefix:
        import fs from "node:fs";
        import path from "node:path";
        import http from "node:http";
    
    It clearly indicates:
        This is a Node built-in module.


13. Three kinds of modules
    Node can resolve different types of modules.
    1. Core modules:
        Provided by Node:
            require("fs");
            require("http");
            require("path");
    2. Local modules:
            require("./utils/helper");
        The ./ tells Node this is a local path.
    3. Third-party modules:
        Installed through npm:
            const express = require("express");
                For example:
                    npm install express
                Then:
                    const express = require("express");


14. Why ./ matters
    require("./math") means:
        Looking for a local module.
    require("math") means:
        Resolve a package/module named math.
    So this distinction is very important.


15. Module resolution
    When Node encounters:
        require("./math");
    it needs to determine what file it means.
    Conceptually it looks for appropriate files such as:
        math
        math.js
        math.json
        math.node
    For packages:
        require("express");
    Node searches through node_modules and package metadata to resolve the package entry point.

    Node has a module resolution algorithm that determines whether a request refers to a built-in module, local file, or package and then loads the appropriate module.


16. Module caching — VERY important
    Suppose:
        counter.js
            let count = 0;
            count++;
            module.exports = count;
        app.js:
            const counter1 = require("./counter");
            const counter2 = require("./counter");
            console.log(counter1);
            console.log(counter2);
        You might expect:
            1
            2
        But you'll get:
            1
            1
    Why?:
        Because CommonJS modules are cached after they are loaded.
    Conceptually:
        require("./counter")
                ↓
        Load module
                ↓
        Execute module
                ↓
        Cache result
                ↓
        Return exports
    Second:
        require("./counter")
                ↓
        Already cached
                ↓
        Return cached exports
    The module isn't executed again.


17. Why module caching matters in real applications
    Imagine:
        // db.js
        const connection = createDatabaseConnection();
        module.exports = connection;
    Multiple files do:
        require("./db");
    We generally don't want every import to create another database connection.
    Module caching can help maintain a shared module instance.
    This is one reason you'll often see things like:
        const db = require("./db");
    used across an application.


18. Practical backend example
    A basic architecture:
        src/
        │
        ├── app.js
        │
        ├── controllers/
        │   └── userController.js
        │
        ├── services/
        │   └── userService.js
        │
        └── utils/
            └── response.js

    userService.js:
        async function getUser(id) {
            // database logic
            return {
                id,
                name: "Dharitri"
            };
        }

        module.exports = {
            getUser
        };

    userController.js:
        const userService = require("../services/userService");

        async function getUser(req, res) {
            const user = await userService.getUser(req.params.id);

            res.json(user);
        }

        module.exports = {
            getUser
        };

    Notice the dependency flow:
        Controller
            ↓
        Service
            ↓
        Database

    This is a much better design than putting everything inside the route handler.


19. Circular dependencies
    Suppose:
        A → B
        B → A
    For example:
        // a.js
        const b = require("./b");
    and:
        // b.js
        const a = require("./a");
    Now we have a circular dependency.
    Node can partially initialize modules in this situation, which can lead to unexpected undefined values or partially initialized exports.
    Example architecture:
        controller
        ↓
        service
        ↓
        repository
        ↓
        service
    That kind of circular dependency is usually a design smell.
    Better to restructure your dependencies.


20. Interview questions
    Q1. What is a module in Node.js?
        A module is a reusable and encapsulated unit of code that can expose functionality to other modules through an export mechanism.

    Q2. What are CommonJS and ES Modules?
        They are two module systems supported by Node.js. CommonJS uses require and module.exports, while ES Modules use import and export.

    Q3. What is module.exports?
        module.exports defines the value that a CommonJS module exposes when another module imports it using require().

    Q4. Difference between exports and module.exports?
        Initially exports references module.exports, so adding properties through exports works. But reassigning exports breaks that reference. module.exports is the actual value returned by require().

    Q5. Are Node modules cached?
        Yes. CommonJS modules are cached after their first load, so subsequent require() calls generally return the cached exports rather than executing the module again.

    Q6. Why is module caching useful?
        It avoids repeatedly executing the same module and can allow shared module-level state, such as a database connection or configuration object.

    Q7. What is the difference between .cjs and .mjs?
        .cjs explicitly indicates CommonJS, while .mjs explicitly indicates an ES Module.

    Q8. Can Node.js use ES Modules?
        Yes. Node.js supports ES Modules using mechanisms such as "type": "module" in package.json or the .mjs extension.
